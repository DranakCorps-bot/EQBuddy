## 1. One new key: "the v2.0.7 switch-on has happened"

Measured on `main` at `c44c0ea8` (`TelemetryHeartbeat.cs` 83–114). These all write the same
bytes (`PromptShown` true, `Enabled` false, `InstallId` null):

- the old build's "Not now" / Esc / ✕ (`Decline`);
- the v2.0.6 notice's Turn off (`Decline`);
- the v2.0.6 Options toggle off (`OptOut`);
- a confirmed delete (`DeleteConfirmed` = `OptOut`).

`LastSeenVersion` does not separate them either: an old "Not now" user who opened v2.0.6
carries `2.0.6` too. **So no rule over today's keys can turn a past "Not now" on and keep a
v2.0.6 Options-off off.** That fact drives the one decision below.

**D1 adds one key**, `TelemetryOnByDefaultApplied` (bool, default false; D1 may pick a better
name), on `AppSettings` beside the other three, written only through `TelemetryHeartbeat`
(trap 47). It means "this profile has been through the v2.0.7 switch-on". The rule, decided in
`TelemetryHeartbeat` and nowhere else:

- **Key false and telemetry off**: the launch **turns telemetry on** (`OptIn`: fresh id) and
  shows the one-time note. The key is written **true** in the same save. That covers two shapes
  on disk. A never-answered install has `PromptShown` false. A past "Not now", a v2.0.6 turn-off
  and a confirmed delete have `PromptShown` true, and those are the ones that cannot be told
  apart.
- **Key false and telemetry already on** (said yes before): nothing changes, the note shows
  once, the key is written true.
- **Key true:** the setting is the player's. Off means the Options toggle (or a delete) turned
  it off on v2.0.7 or later, and it **stays off for good**. No launch rule ever flips it again.
- **Isolated profile** (E2E, `shoot.ps1`): no switch-on, no note, no send, key untouched.
  **`NoEndpoint` build**: no switch-on and the key stays false, so the one-time switch-on is
  not spent on a build that cannot send (DRA-1980's rule for the old prompt, same reason).

`DeadSettingTests` (trap 20) gets the writer and the reader in the same commit. The key
replaces the old prompt's job. `TelemetryPromptShown` keeps its writers for compatibility; D1
decides whether it has a reader left and says so.

**Decided, and D1 logs it in `DECISIONS.md`: the v2.0.6 window is switched on too.** Anyone
who turned telemetry off *on v2.0.6* (tagged 2026-10-18 11:08 AM CT, so a window of hours to
days before v2.0.7) wrote the same bytes as a "Not now", and v2.0.7 turns them on. Order 2's
"explicit off via Options stays off" is met from v2.0.7 on; it **cannot** be met for that
v2.0.6 window from disk. The default could have gone the other way: leave every off profile
off, which keeps the v2.0.6 promise exactly and leaves every past "Not now" uncounted, the
opposite of both orders. It also switches a profile that completed a confirmed delete back on,
with a fresh id, and the note and What's new say so. Landed on switch-on, with two protections
for that cohort (both are Challenger conditions, DRA-2011):

1. **The first beat waits, across relaunches, until the player has had the note.** The
   switch-on that turned an OFF profile on also persists "switched on, first beat not sent
   yet". A second new key, or a state of the first one; D1 picks, written only through
   `TelemetryHeartbeat`. While it is set, no process beats at the epoch: the first beat waits
   one cadence (5 min, the existing interval) from the start of **each** launch, and the note
   stays up on every launch until that beat has gone. The flag clears when the beat is sent, or
   when the player turns telemetry off (that off is final, as any key-true off). So a restart
   straight after the update sends nothing at once, and the note does not leave before the
   player could act on it. An install that was already on keeps DRA-381's immediate beat, and so
   does every launch after the first beat. If D1 measures that the delay moves a §3 definition
   (sessions, active days), it stops and escalates rather than dropping the hold.
2. **One extra sentence in the note, only where `PromptShown` was already true** (a past "Not
   now", a v2.0.6 off, a confirmed delete; never a never-answered install and never an install
   that was already on). In sense: *"This version turns telemetry back on even if you said
   'Not now', turned it off, or deleted your data before. Only turning it off from now on stays
   off. Turn it off again in Options if you want it off."* It must not say the last version
   failed to save the choice. It did save it, and this version chooses not to keep it. Wording
   is D1's, in `TelemetryCopy`; the sense is fixed here.

A never-answered install gets the generic note only.

Reviewer, Challenger or Helm can veto at the last look. A veto that keeps v2.0.6-era offs off
also keeps every past "Not now" off (same bytes), which reverses the Founder's order, so it goes
back to the Founder as a ranked ask, not a quiet change.

## 2. D1 — the client, the note, the requirement text, What's new

**Consent rule (`TelemetryHeartbeat`, still the ONE policy).**
- The §1 rule replaces the first-open prompt's decision. **The blocking prompt / notice window
  is removed** from the launch path (order 2). No window waits on the player; no Turn off
  button exists anywhere except the Options toggle.
- **Off stops sends at once.** `SetEnabled(false)` keeps its disarm-before-save order and
  destroys the id, as today.
- **Unchanged and asserted unchanged:** an isolated profile never sends and never sees the
  note; a `NoEndpoint` build spends nothing; re-enabling mints a fresh id; the delete action;
  the Options toggle and its status line.

**The note.** Non-blocking: a dismissible line or banner on the widget at the first launch
after the update, under the header where the eye lands (trap 44). It goes when it is dismissed
or on the next launch, **except** while §1's first beat is still held: then it shows on every
launch until that beat is sent or telemetry is turned off. It says, in plain words: telemetry is on; what it is for (*understanding
how many people use EQBuddy and how, so David can plan support and resources*); the three
fields and what is never sent; where to turn it off by its real label (`Options → Behavior →
Help improve EQBuddy`), with a button that opens that page (a door, not a gate). Plus the §1
cohort sentence when it applies. D1 picks the surface and owns the layout; a shot of the note
in both forms ships with it (`shoot.ps1`, Solarized once).

**Options.** The caption under the toggle states plainly that telemetry is on by default for
every install, what it is for, and that off here is final. Every sentence lives in
`UI.Shared/TelemetryCopy.cs`.

**Payload frozen.** `PayloadKeys`, `Payload`, `PayloadFor` and `TelemetrySender`'s body are not
touched. Reviewer refuses a diff to any of them. The new key never rides the wire.

**Requirement text.** `docs/v2/telemetry.md`: amend TEL-001 in place *"as amended by DRA-2010
(Founder, 2026-10-18)"*: telemetry is on by default for every v2.0.7 install, past "Not now"
included; there is no consent prompt; the only off is the Options toggle (or a delete), and it
is final. Strike the opt-in prompt and "a past 'Not now' is still final" clauses (around lines
55–66, 476, 628, 667, 1016) the same way DRA-1980 did, and record the new key, the held first beat, and
the v2.0.6-window decision.

**What's new.** One v2.0.7 entry: telemetry is now on for every install, including anyone who
said "Not now" before; why (the install-base sentence above); the three fields and what is
never sent; the Options path by its real label; that turning it off deletes the id and is
final; and the §1 sentence: earlier offs ("Not now", an Options off, a confirmed delete) are
turned back on, and only an off made from v2.0.7 on stays off. No reporter to credit
(Founder order).

**Tests, prove-failed.** `TelemetryHeartbeatTests`: each §1 case (key false/off, key
false/on, key true/off, key true/on, isolated, `NoEndpoint`) → its outcome, each mutated once;
the switch-on writes the key and a fresh id in one save; a key-true off profile is never
flipped; the held first beat applies only after a switch-on from off, pinned with a negative
for the already-on case; **a relaunch while it is held does not beat at the epoch** and still
shows the note; the hold clears on the first sent beat and on a turn-off; toggle off still
disarms before save. `TelemetryCopyTests` pin the cohort sentence to the
`PromptShown`-already-true switch-on only, with negatives for never-answered and already-on,
and refuse any "could not save" wording. E2E: the dump word for the
switch-on and the note, and an isolated launch proves neither happened.

**V-level:** V2 (affected suites + `check.ps1`), then CI's two required checks.
