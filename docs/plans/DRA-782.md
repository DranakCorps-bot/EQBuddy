Two measured facts shape the design:

- **PR titles are not plain language and most are not about the app.** Of the 10, six
  are `plan(...)`, `ops(...)`, `docs(...)`. The `src/` test separates them exactly, so
  the page leads with WhatsNew text (written for players) and lists app PRs under it,
  with the process PRs folded into a count.
- **The dev stamp lives only on the Founder's PC.** Nothing on GitHub can read it. What
  the repo CAN say is "main is at `abc1234`; auto-roll installs it within about ten
  minutes; your Options footer shows `dev abc1234` when you have it." That turns his
  footer into the check, with no new plumbing.

## 2. Where the page lives — ruling R1 (signed default: a pinned issue)

**Default: one pinned, locked GitHub issue labelled `dev-status`, whose BODY a workflow
rewrites on every merge to `main` and every published release.** The README links to it.

Why not a committed `DEV-STATUS.md` (the card's other suggestion): `main` requires
`build-and-test` + `e2e-windows` with `enforce_admins` ON (DRA-228). A file that must
change on every merge can only land through a PR, so "auto-generated" becomes one bot PR
per merge — double the PR traffic, each one conflicting with the next — or a bypass of
the protection, which C5 would rightly stop. An issue body is outside the protected
tree: it updates in seconds, needs no PR, and keeps `main`'s history free of churn.
Rejected alongside: the wiki (Actions cannot push to it reliably with `GITHUB_TOKEN`),
the Pages landing site (player-facing marketing; Planner may not touch Pages), a
pre-release (touches the release channel).

**Public visibility (consequence list item 3), assessed:** the repo is public, so
anything "on the repo" is public — the Founder asked for it there. Every fact on the page
is already public (merged PRs, release tags, WhatsNew text that ships with the next
release). The page carries no promise: its header says *"Merged to main, not released.
Nothing here is a commitment about what the next release contains or when."* The issue is
**locked** so it does not become a comment thread. If Helm or the Founder want it private
instead, the same script writes to a file the Founder reads locally — a one-line change
of output target, not a redesign.

## 3. What the page says (in this order)

1. **Live:** latest non-prerelease release — tag, date, link.
2. **Dev build:** `main` head short sha + commit date, the next version from
   `Directory.Build.props`, and the one sentence about auto-roll and the Options footer.
3. **Coming in the next release (plain language):** every `WhatsNew.json` entry whose
   `version` is greater than the live tag, verbatim. If none: "No What's-new entry yet."
4. **App changes merged since live:** PRs from the first-parent merge list whose files
   touch `src/` — `#N title` (link), newest first.
5. **Needs your testing:** (a) every app change in 4 — all of it ships on the next
   release go, so all of it is untested by him until he says otherwise; (b) every OPEN PR
   labelled `needs-founder-smoke` (the "PR still awaiting his smoke" CLAUDE.md already
   names; the label is new, applied by whichever seat asks him to smoke a PR, removed when
   he signs off). Empty states say so in words, never a blank.
6. **Other merges since live:** "N process/docs changes (plans, ops, docs)" — a count
   in a collapsed `<details>` list, so they are findable but do not bury 3–5.
7. **Footer:** "Generated <UTC time> from `main` @ `<sha>` by `.github/workflows/dev-status.yml`."
   If the workflow ever fails, this line is how staleness shows: the page never pretends
   to be current.

## 4. Delivery (one slice)

**D1 — Sr Executor.** Files:

- `scripts/dev-status.ps1` — gathers the facts with `gh`/`git`, renders markdown through
  ONE pure function `Format-DevStatus` (inputs in, string out), and `-Publish` finds the
  open `dev-status` issue (creates it if absent, labelled + locked) and replaces its body.
  `-SelfTest` runs `Format-DevStatus` over fixed inputs and asserts: the live tag; the
  WhatsNew version filter (an entry AT the live version is excluded, one above it
  included); the `src/` split; every empty-state sentence; the footer. **Prove-fail it**
  (trap 34): break the version filter and the `src/` split once each, record both reds
  in the PR body.
- `.github/workflows/dev-status.yml` — triggers `push: main`, `release: published`,
  `workflow_dispatch` ONLY. **Never `pull_request` / `pull_request_target`**: no fork code
  ever runs near the write token. `permissions: contents: read, issues: write,
  pull-requests: read`. `concurrency: dev-status, cancel-in-progress: true` so the latest
  merge wins. `fetch-depth: 0` (it needs the tag).
- `scripts/check.ps1` + `.github/workflows/ci.yml` — add `dev-status.ps1 -SelfTest`
  beside the existing autoroll-guard step.
- `README.md` — one line under **For developers**: "What's on `main` vs the live release:
  [dev status](…/issues?q=label%3Adev-status)" (a label query, so the link never needs
  the issue number).
- `docs/TestPlan.md` — one row for the selftest.

Executor also, once, after merge: create the `needs-founder-smoke` label, run the
workflow (`workflow_dispatch`), `gh issue pin` the issue it made, and post the issue URL
on DRA-782.

**Not in scope:** no change to `auto-roll.ps1`, the dev stamp, `release.ps1`, WhatsNew
rules, branch protection, Pages or any release. No per-PR plain-language rewriting — the
plain language is WhatsNew's, which already has an owner and a rule.

## 5. Done bar

- PR merged on green `build-and-test` + `e2e-windows`, selftest prove-fail recorded.
- First `dev-status` run on `main` is green; the issue exists, is pinned, locked and
  labelled; its body shows **v2.0.3 live**, `main`'s current sha, the **2.0.4** WhatsNew
  entry, the app PRs since v2.0.3 (#992, #1012, #1022, #1023 at time of writing, plus
  anything merged since), and the process-PR count.
- One more merge to `main` visibly rewrites the body (footer sha moves) with no human step.
- DRA-782 carries the issue URL and a plain two-line note for the Founder: where the page
  is, and that his Options footer `dev <sha>` matching the page's sha means he has the
  build.

## 6. Risks

- **`gh` on the runner rate-limits** — ten-odd calls per run, far below the hourly limit
  for `GITHUB_TOKEN`.
- **Two merges seconds apart** — `cancel-in-progress` drops the older run; the newer one
  renders the newer state. Correct by construction.
- **Someone edits the issue by hand** — the next run overwrites it. Intended: the page
  has one writer (trap 4).
