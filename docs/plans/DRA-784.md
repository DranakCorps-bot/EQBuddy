## 2. What can and cannot be detected for Mac-via-Wine (said plainly)

- **Under Wine, Windows APIs report Windows.** `Environment.OSVersion` returns the
  Windows version the Wine prefix is configured to imitate (e.g. 10.0.19045). Nothing in
  today's payload can tell a Mac from a PC.
- **Wine CAN usually be detected**, by asking `ntdll.dll` for the export
  `wine_get_version`. Present ⇒ Wine. Wine, CrossOver, Whisky and Proton all expose it by
  default.
- **The host OS CAN usually be read** from the sibling export `wine_get_host_version`,
  whose first value is the host kernel name: `Darwin` ⇒ macOS, `Linux` ⇒ Linux.
- **What cannot be detected:** a prefix configured to hide Wine's exports (Wine's
  `HideWineExports` setting, used to dodge anti-cheat) looks exactly like Windows and will
  be counted as Windows. Wine on FreeBSD or anything other than Darwin/Linux is counted as
  "Wine, other host". There is no reliable way to separate a real Windows PC from a
  well-hidden Wine prefix, and the report must say so rather than present the Windows
  share as exact.
- **Native macOS/Linux builds do not exist** for Evolved (Windows-only since 2026-09-04),
  so "Linux later" is a bucket that exists and reads 0 unless Wine-on-Linux is reported.

## 3. Privacy stance

OS is coarse and non-identifying, and the `os` field is already disclosed and stored.
D1 adds no field, no column of raw data, and nothing sent: it counts an existing value.
D2 changes the VALUE's form within the same key and the same 64-char bound, adding at
most the host FAMILY (`macOS` / `Linux` / `other`) — deliberately **not** the Wine
version, the host kernel version or the distribution, all of which would make the field
less coarse. The prompt's body sentence ("your OS … in the form the system reports it")
stays true and becomes truer; the three "your Windows version" sentences would become
false for a Wine player, which is why D2 waits on the Founder.
