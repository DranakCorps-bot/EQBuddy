## 1. What changes, and what does not

**Changes:** `scripts/signing.ps1` gains a second way to authenticate to Azure
Artifact Signing — a service principal (SP) whose credential is a certificate on
David's PC — and prefers it. The release seat (DRA-675) stops needing a human to
refresh an `az login` session.

**Does not change (CLAUDE.md signing rule, verbatim in force):**

- Every artifact is signed and **verified** — `Get-AuthenticodeSignature` is `Valid`
  **and** has a `TimeStamperCertificate`. `Invoke-EqSign` is not touched.
- No bypass, no `-SkipSign`, no warn-and-continue. If neither credential works,
  `Initialize-EqSigning` throws before the publish, exactly as it does today.
- `az login` stays a **working fallback**: a broken SP with a live `az` session still
  signs (and says loudly which identity signed). A fallback here is always to another
  *signed* path, never to an unsigned one.
- Who gives the release GO — that is DRA-675 D1's item-2 reword, not this card.

## 2. Measured before planning (2026-10-01, this run)

- **The pinned dlib (`Microsoft.ArtifactSigning.Client` 1.0.128) builds a
  `DefaultAzureCredential` and reads `ExcludeCredentials` from the metadata file.**
  Evidence: the strings `DefaultAzureCredentialOptions`, `ExcludeCredentials`,
  `ExcludeAzureCliCredential`, `ExcludeAzurePowerShellCredential`,
  `ExcludeEnvironmentCredential`, `ExcludeManagedIdentityCredential`, … and
  `AccessToken` are all present in `Azure.CodeSigning.Dlib.Core.dll`. That is a
  string-level measurement — the **behaviour** is D1 step 0's to measure, not assumed.
- `az` is installed and the session is live (`user.type = user`). **Az PowerShell
  (`Az.Accounts`) is NOT installed.**
- `artifact-signing.json` (gitignored, repo root) holds exactly `Endpoint`,
  `CodeSigningAccountName`, `CertificateProfileName`, `CorrelationId`.

## 3. Credential shape — the choice and why

**Chosen: an Entra app registration + service principal with a CERTIFICATE
credential whose private key is NON-EXPORTABLE, in `Cert:\CurrentUser\My`, TPM-backed
where the PC has a TPM 2.0 (`Microsoft Platform Crypto Provider`), software KSP
otherwise.**

| Option | Verdict | Why |
|---|---|---|
| SP + certificate, non-exportable, CurrentUser store | **CHOSEN** | Nothing copyable sits on disk: the key can be *used* by David's Windows user but not *exported*, so a leaked repo, backup, log or OneDrive sync carries no *key* that signs. **One thing copyable does sit on disk (C-2):** `Connect-AzAccount` persists an Az context/token cache under the user profile, and that cache is a **bearer** for the section 7 lifetime (~60-90 min of access token; longer if it holds a refresh token, which D1 measures under K3). It is named here so nobody reads "non-exportable" as "nothing that signs can leave the PC". TPM-backed, it cannot leave the machine at all. |
| SP + client secret | Rejected | A secret is a string: it lives in an env var or a file every process and every backup can read, and it lands in logs. Max lifetime 24 months and it is the leak shape every Corps doc warns about. |
| SP + certificate as a PFX/PEM *file* (`AZURE_CLIENT_CERTIFICATE_PATH`, `az login --service-principal --certificate`) | Rejected | It is the client secret again with extra steps — the private key is a copyable file. This is why the `EnvironmentCredential` / `az` routes are not the primary path: neither can use a cert from the store by thumbprint. |
| Managed identity | Does not fit | Only exists on an Azure resource or an Azure Arc-enrolled machine. Arc on a home Windows 11 PC is an unsupported-for-production agent with a machine-wide identity any admin process can use — broader than this, for nothing. |
| Federated / workload identity | Does not fit today | Needs an OIDC issuer the tenant trusts (e.g. GitHub Actions). It is the right answer **if signing ever moves to CI**, with no long-lived credential at all — a separate decision (releases run on David's PC, signing stays there). Named so nobody re-derives it. |

**How the certificate reaches Azure without becoming a file:** `Az.Accounts`'
`Connect-AzAccount -ServicePrincipal -CertificateThumbprint` signs the client
assertion with the store key (works for non-exportable keys). The dlib's
`DefaultAzureCredential` then picks the session up through
`AzurePowerShellCredential`. So D1 installs **`Az.Accounts` only, pinned**
(`-RequiredVersion`, `-Scope CurrentUser`) — the same rule as the pinned dlib: a
signing toolchain that moves on its own produces output you cannot reproduce.

## 4. Least privilege

- **One role: `Artifact Signing Certificate Profile Signer`** (the built-in role
  previously named `Trusted Signing Certificate Profile Signer` — same role, the
  portal shows whichever name the tenant has; D1 records the role's GUID from
  `az role definition list` on the card so the name drift cannot matter).
- **Scope: the one certificate profile only** —
  `…/Microsoft.CodeSigning/codeSigningAccounts/<CodeSigningAccountName>/certificateProfiles/<CertificateProfileName>`,
  read from `artifact-signing.json`. **Not** the account, resource group or
  subscription. No `Reader`, no `Contributor`, no Graph/API permissions on the app.
- What the SP can do if stolen: sign files as `FlossworksCross-Stitch`. That is
  serious (§7 exists for it) — and it is everything the SP can do. It cannot create
  profiles, read other resources, or touch identity.
- D1 asserts the scope: `az role assignment list --assignee <appId> --all` returns
  exactly one row, that role, that scope. Pasted on the card.

## 5. Where it lives, who can use it, expiry

- **On disk, nothing secret.** A new gitignored `artifact-signing-identity.json`
  beside `artifact-signing.json`: `TenantId`, `ClientId`, `CertificateThumbprint`.
  None of these signs anything. `.gitignore` gets the line in the same commit.
- **The key:** `Cert:\CurrentUser\My`, non-exportable. **Who can use it:** any
  process running as David's Windows user (that includes every agent seat on this
  PC) and any local admin. **Who can copy it:** nobody (non-exportable; with TPM,
  not even an admin). Stated plainly because it is the real boundary: the
  protection is "cannot leave the PC", not "only the release seat can use it".
- **Lifetime: 12 months.** Chosen over 6: each rotation needs a portal-side upload
  (or a scripted one under David's `az` session, §6), and a shorter cycle buys little
  when the key cannot be copied. Default could have gone 6; logged as such.
- **Expiry handling in `signing.ps1`:** cert `NotAfter` < 30 days → loud `WARN`
  line and the release seat files a Planner rotation card (signing proceeds).
  Expired, missing, or `HasPrivateKey` false → the SP path is skipped with a line
  saying why, and the `az` fallback is tried. Neither works → **throw** (today's
  behaviour). The seat then stops and files one Founder card ("Founder: …",
  recommended default included). **Never unsigned.**

## 6. D1 — the build (Sr Executor, one PR)

0. **Measure before building `signing.ps1` (stop seam).** Runs right after step 1
   creates the SP (no throwaway SP), and **only after `az logout` (C-1)** so David's CLI
   session cannot be the credential that answers: sign a scratch copy of an already-shipped binary with `ExcludeCredentials` set to everything except
   `AzurePowerShellCredential` and confirm `Valid` + timestamp **and** that the
   signing log names the SP, not David. **"Names the SP" is an Azure-side observation,
   never a line `signing.ps1` prints about itself (C-1, trap 84):** paste the `appid`
   claim of the token the same Az context is issued for the signing resource
   (`Get-AzAccessToken`, decoded) and, where the tenant exposes it, the Entra
   service-principal sign-in entry for that appId at that minute. **The same step must
   FAIL with a wrong thumbprint and with the cert removed (C-3)** — a sign that
   succeeds either way means another credential answered. If the dlib does not honour
   `ExcludeCredentials` or does not reach the Az PowerShell session, **stop and hand
   to Planner** — the named alternative (minting a token in `signing.ps1` and passing
   the dlib's `AccessToken` metadata field in a per-run temp file) writes a bearer
   token to disk and is a plan change, not an executor call.
1. **Create the identity — scripted, under David's existing `az` session**
   (`scripts/signing-identity.ps1 -Create`, idempotent): generate the non-exportable
   cert (`New-SelfSignedCertificate -KeyExportPolicy NonExportable`, TPM provider
   first, 12-month `NotAfter`), export the PUBLIC `.cer` only, `az ad app create`,
   `az ad sp create`, `az ad app credential reset --cert @<cer> --append`,
   `az role assignment create` at the profile scope (§4), write
   `artifact-signing-identity.json`, delete the `.cer`. **(C-4)** `-Create` then runs
   `az role assignment list --assignee <appId> --all`; anything other than exactly one
   row (that role, that profile scope) → it revokes (section 7 steps 1-2) and **stops**.
   No fix-forward. The Founder's ruling
   authorises creating this login; doing it by script is how it stops being his
   keystroke. If any `az ad`/role call is refused (tenant policy, rights, expired
   session), **stop** and file the §8 Founder card — no workaround.
2. **`scripts/signing.ps1`:** replace `Assert-EqAzureSignIn` with
   `Resolve-EqSigningIdentity`, returning `ServicePrincipal` or `AzureCli` (a value,
   trap 81 — never `$null` for three worlds). SP path: `Connect-AzAccount
   -ServicePrincipal -CertificateThumbprint … -Tenant … -ApplicationId …`. Write a
   **per-run copy** of the metadata (no secrets in it) to a temp file with
   `ExcludeCredentials` set so only the resolved credential can answer, pass that as
   `/dmdf`, delete it in `finally`. Print `Signing identity: <SP appId | user>` so the
   release log says who signed. `Invoke-EqSign`'s verify block is unchanged.
3. **`-selftest` with prove-fail mutants** (trap 34/78), in `check.ps1`, no Azure
   calls: the resolver picks SP when the identity file + valid cert exist; falls to
   `AzureCli` on missing/expired/no-private-key cert; **throws** when both are
   absent; the per-run metadata excludes the unused credential. Mutants: a resolver
   that returns `SkipSign`/`$null`, an expiry check that is ignored, and an exclude
   list left empty — each must redden it.
4. **`signing-identity.ps1 -Rotate`** (new cert, `--append`, first sign with it, then
   remove the old key credential) and **`-Revoke`** (§7). Both documented in
   `docs/ops/release-seat.md` (DRA-675 D1's file) under a "Signing login" heading.
5. **CLAUDE.md Commands block:** the `az login` paragraph becomes "the release signs
   as a service principal (`signing-identity.ps1`); `az login` is the fallback and
   the one human step only if both fail". Trap-free wording, no second copy of §7.
   `DECISIONS.md` appended entry (12 months vs 6; scripted creation vs portal).

## 7. Revocation runbook (if the credential leaks or the PC is lost)

Fastest first; any ONE of the first two stops new signatures.

1. `pwsh -NoProfile -File scripts/signing-identity.ps1 -Revoke` (from any machine
   with David's `az` session): `az ad sp delete` — kills the SP outright.
   **Portal equivalent:** Entra ID → App registrations → "EQBuddy Release Signer" →
   Delete. Effect: new tokens refused immediately; a token already issued lives up
   to ~60–90 minutes.
2. Belt and braces: `az role assignment delete` on the profile scope (the SP cannot
   sign even if step 1 is undone).
3. If a malicious file may have been signed in that window: Artifact Signing →
   the profile → open a support case to revoke the certificate(s) issued in the
   window. Certificates live 3 days, so the exposure window is bounded, but
   revocation is what un-trusts an already-signed file. Planner files the card;
   this is consequence-list territory (public trust) and Helm pages David.
4. Remove the key from `Cert:\CurrentUser\My` on the PC; re-run `-Create` when safe.

**Time to kill:** minutes for steps 1–2 by script; worst case ~90 minutes of residual
token life. Step 3 is days and is why §4 keeps the SP able to do nothing else.
