## 1. What exists today (measured on `main` at 8cf5658d)

- **`scripts/install-local.ps1 -Evolved -Install`** builds whatever tree it runs
  from, signs `EQBuddy.exe` (verified + timestamped, no bypass), copies the installed
  exe to `EQBuddy.previous.exe` (the Start menu's "(previous version)" rollback), swaps
  in the new one, checks the hash, and relaunches on the real profile. It refuses when
  no install exists. **This is 90% of the job.**
- **Defect for this use: it closes the running app BEFORE `dotnet publish`.** A
  failed build today leaves the Founder with no app running. Fine when a person is
  watching; wrong when nobody is.
- **Signing runs unattended already.** `signing.ps1` prefers the service principal
  (DRA-679/DRA-695): a certificate in `Cert:\CurrentUser\My`, no `az login`, no
  prompt. So a scheduled run under his user can sign. Nothing else is needed.
- **Scheduled tasks are how this PC runs things.** Ten `\Dranak - …` tasks exist under
  his user (Ensure Paperclip, Ollama GPU Guard, the Hermes gateways). One more is the
  house pattern, not a new mechanism.
- **No build stamp exists.** The app shows `Assembly.GetName().Version` (`2.0.x`)
  everywhere; nothing names the commit.
- **Releases cannot happen by accident.** `release.ps1` refuses a 2.x tree and
  `evolved-channel-guard.ps1` (in `check.ps1` and its own CI step) keeps it that way;
  there is no flag that opens the channel (DRA-252 measured this).

## 2. Trigger — a scheduled poll, every 10 minutes

**Pick: a Windows scheduled task `\Dranak - EQBuddy Auto-roll`, the Founder's user,
"run only when user is logged on", every 10 min and at logon.** It runs
`scripts/auto-roll.ps1` from a dedicated clone, `C:\Users\david\source\EQBuddy-autoroll`.

Rejected: a **post-merge git hook** — merges happen on GitHub, so no local git event
ever fires. A **GitHub webhook** — needs an inbound port to the PC. A **resident
watcher** — one more process to keep alive, for nothing a 10-minute poll does not do.
"Logged on only" because the job must relaunch a desktop app on his desktop; when he
is logged off there is nothing to overwrite.

Each run: `git ls-remote origin refs/heads/main` (cheap). Same SHA as the last good
roll → exit. New SHA → one roll of the newest commit; five merges in ten minutes are
one roll, not five.

**The dedicated clone is the build tree and nothing else.** No agent works in it. Its
push URL is set to an invalid value (`git remote set-url --push origin DISABLED`), and
each roll does `git checkout --detach <sha>` + `git clean -fdx` (keeping the gitignored
`tools/` and `artifact-signing.json` it needs), so a stray file can never ride into a
build.

## 3. The roll — build first, close last

Reorder inside `install-local.ps1` (both modes benefit; one code path, trap 4):

1. Build and sign into `dist\publish`. **The running app is untouched.** Any failure
   here stops the roll, and the Founder never notices.
2. Close the copy holding the Evolved profile (graceful, 15 s, then force — the
   existing `Close-EqBuddyGracefully`, so his session still finalizes into
   `history.db`). Remember whether one was running.
3. Swap (existing: previous → `EQBuddy.previous.exe`, new in, hash read back).
4. Relaunch **only if it was running** (Founder's item 3). If it was not, leave it
   closed — the next time he opens it, it is the new build.
5. **Liveness check:** when it was relaunched, the new process must still be alive
   at 20 s. If the swap's hash check fails, or the new build dies inside that window,
   copy `EQBuddy.previous.exe` back over `EQBuddy.exe`, relaunch it, and record the
   failure. That is "keep the last good build" in one rule.

A SHA that failed is not retried until `main` moves again (no failure every ten
minutes). One retry is allowed for a failure in step 1 that looks transient (network
restore of the signing toolchain); the log says which.

## 4. Never a release — how that is guaranteed

Five layers, each sufficient on its own for the publish half:

1. `auto-roll.ps1` calls `install-local.ps1 -Evolved -Install` and nothing that
   publishes. **New guard `scripts/autoroll-guard.ps1`** (in `check.ps1` + CI):
   a forbid-scan of `auto-roll.ps1` for `release.ps1`, `gh `, `git push`, `git tag`,
   `OneDrive`, `Invoke-RestMethod`/`Invoke-WebRequest` with a write method — **paired
   with a must-list** (it does call `install-local.ps1 -Evolved -Install`, trap 34),
   and both arms prove-failed against committed mutants in a `-selftest` (trap 78).
2. `release.ps1` refuses a 2.x tree and `evolved-channel-guard` enforces it (existing).
3. The clone cannot push (push URL disabled).
4. The task runs as the Founder's non-admin user; it needs no `gh` token and holds no
   release credential beyond the signing certificate it already uses for local builds.
5. The installed app's updater only offers a NEWER release; a dev build carries
   `Directory.Build.props`' version, never behind the last tag (existing, unchanged).

## 5. Ruling R1 for Helm — sign the auto-rolled build, or not

The card's item 2 lists "signing credential use" beside tag/release/OneDrive.
**Planner reads that item's purpose as "this can never publish"**, and recommends
**SIGN**: signing a local exe publishes nothing; it is what his daily driver already
does by hand today; and an unsigned build is what re-triggered Defender's cloud-ML
false positive (`install-local.ps1`'s own comment), so an unsigned auto-roll would test
a different artifact from the one players get and could get quarantined on his PC.

- **(a) SIGN — recommended.** Reuse the existing service-principal path. A signing
  failure (e.g. the certificate expires) is a step-1 failure: last good build kept,
  failure reported.
- **(b) UNSIGNED.** Honours the card's text literally. Costs a new unsigned branch in
  `install-local.ps1` (C5 fires, Challenger walk first) and the Defender risk above.

Helm rules R1 at the SIGN. If Helm judges it a security call that is the Founder's,
Helm takes it to him; the plan does not wait on him otherwise.

## 6. Build stamp — three places, loud

- **A file beside the exe**: `EQBuddy.build.json` — `{ sha, subject, mergedPr,
  builtAt (local + UTC), result }`, and the job's state at
  `%LOCALAPPDATA%\EQBuddy Evolved\autoroll\state.json` (last good SHA, last attempt,
  last result, log path). Logs rotate (keep 20).
- **A Windows toast on every roll**: "EQBuddy updated to main `abc1234` — <PR title>"
  or "EQBuddy auto-update FAILED at `abc1234` — still running `def5678`". Plain
  WinRT notification from PowerShell, no module install (the Documents folder refuses
  them on this PC).
- **In the app, dev builds only**: `auto-roll` passes `-p:SourceRevisionId=<sha>` and
  `-p:EqDevBuild=true`; when that property is set, the Options window footer and the
  Feedback window's version line read `2.0.x · dev abc1234 · Oct 1, 3:56 PM`. A
  release build never sets it, and an E2E row asserts the release configuration shows
  no `dev` marker (committed negative). Not player-noticeable, so no `WhatsNew.json`
  entry.

## 7. Pause switch

- **The Founder:** two desktop shortcuts, "Pause EQBuddy auto-update" and "Resume",
  that create / delete `%LOCALAPPDATA%\EQBuddy Evolved\autoroll\PAUSED`. The toast
  says "paused" once when it takes effect. (Disabling the scheduled task also works;
  it is the fallback, not the documented switch.)
- **Helm, without touching the PC:** the file `docs/ops/autoroll.pause` on `main`.
  The job fetches `main` every run anyway; if that file exists it does not roll. A
  Helm commit (via PR, required checks as always) pauses it; deleting the file resumes.
- **A manual install wins over the robot.** The 2026-09-29 rule also installs "any PR
  still awaiting his smoke" from a local branch. Without care, the next merge would
  overwrite that smoke build within ten minutes. So `install-local.ps1` records the
  SHA it installed; the job **skips while that SHA is not contained in `origin/main`**,
  for at most 48 h. When the PR merges, `main` contains it and auto-roll resumes on
  its own.
