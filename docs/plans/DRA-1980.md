## 1. Can the settings model tell "explicit off" from "never set"? Yes, with no new key

The card asks Planner/Reviewer to confirm this. Measured on `main` at `79694a49`
(`src/EQBuddy.Core/AppSettings.cs` 1059–1078, `src/EQBuddy.UI.Shared/TelemetryHeartbeat.cs`):

| State on disk | How it got there | Reading |
|---|---|---|
| `TelemetryPromptShown = false`, `TelemetryEnabled = false` | never answered: new install, an existing install that never saw the prompt, a prompt closed unanswered (DRA-385), a `NoEndpoint` build | **never set → becomes ON** |
| `PromptShown = true`, `Enabled = false` | "Not now" / Esc / ✕ on the prompt (`Decline`), the Options toggle turned off (`OptOut`), or a confirmed delete (`DeleteConfirmed`) | **explicit off → stays OFF** |
| `PromptShown = true`, `Enabled = true`, valid id | opted in | stays on, same id |

`OptIn` writes `PromptShown = true` too, so no path reaches `Enabled = true` with the flag
unset, and every off-path that is a player action leaves the flag set. **The existing
`TelemetryPromptShown` flag already IS "the player has answered".** No fourth key (Helm's
C-1 §8.3.1 three-key rule stands) and no persisted migration (trap 55).

**Decided, and logged in `DECISIONS.md` by D1:** a "Not now" on the old prompt counts as
an explicit off. The default could have gone the other way ("not now" is not "never"),
which would cover more users. Landed on off, because `SECURITY.md` line 111 publicly
promised *"'Not now' is final"*. Turning a published promise around for the people it
was made to would make us uniquely wrong. The Founder's words ("explicitly turned it off")
fit either reading. Reviewer or Helm can veto at the last look.

## 2. D1 — the client, the copy, the requirement text, What's new

**Consent rule (`TelemetryHeartbeat`, still the ONE policy; trap 47).**
- The first-open YES/NO prompt becomes a **one-time notice**: telemetry is on, here is
  everything it sends (the three fields, the same `TelemetryCopy` payload sentence), and
  where to turn it off. Two actions: **OK** (keep on) and **Turn off**.
- **No heartbeat leaves before the notice has been on screen.** The enable (`OptIn`, which
  mints the id and sets the flag) is written when the notice closes by OK, Esc or ✕. Turn
  off writes `Decline` (flag set, nothing else). A kill or crash before it closes writes
  nothing, so the next launch shows it again and nothing was sent meanwhile. This keeps
  DRA-385's rule ("nothing saved before the answer") and makes disclosure come before the
  first send. Ordering test: the `RunFirstOpen` shape, with the window and disk handed in.
- Upgrade and new install take the same path: an existing never-answered profile sees the
  notice once on the first build carrying this change. That is the upgrade disclosure in
  the app. New installs skip What's new, so the notice is their only disclosure.
- **Unchanged and asserted unchanged:** an isolated profile never sends and never shows
  (`MaySend` / `NotTheProductProfile`); the harness can still only script a decline; a
  `NoEndpoint` build spends nothing; re-enabling mints a fresh id; the delete action.
- **Turning the toggle off stops sends at once**: `OptOut` + `TelemetrySchedule.Disarm`
  in the same handler, and an in-flight beat does not re-arm (`stillArmed` false). This
  works today. D1 adds a test that pins it so the new default cannot loosen it.

**Payload frozen.** `PayloadKeys` and its guard are not touched. A diff to
`TelemetryHeartbeat.Payload`, `PayloadKeys` or `TelemetrySender`'s body is out of scope;
Reviewer refuses one.

**Words.** Every changed sentence lives in `UI.Shared/TelemetryCopy.cs` (the notice, the
Options toggle's label and caption). The Options toggle stays where it is under Options, and
its caption stops saying "off until you turn it on". The words say it is anonymous: a
random id, the app version and the Windows version; no character, chat, log or file
content. They must not say "anonymous" without listing what is sent.

**Requirement text.** `docs/v2/telemetry.md` §1: amend TEL-001 in place, as DRA-336 did:
strike the clauses, mark *"as amended by DRA-1980 (Founder, 2026-10-18)"*, and state the
new rule and the explicit-off reading from §1 above. Amend the "does not authorize
on-by-default" lock to match. TEL-002…TEL-006 unchanged.

**What's new.** One `WhatsNew.json` entry for the release that ships it: telemetry is now
on by default; exactly what is sent (three fields) and what is not; that anyone who said
"Not now" or turned it off before stays off; where to turn it off (Options, by its real
label); and that turning it off also deletes the id. No reporter to credit (Founder ask).

**Tests, prove-failed.** Policy-level in `TelemetryHeartbeatTests`: the three on-disk
states in the §1 table → their outcome, each mutated once; notice ordering (no `OptIn` on
an unanswered close); isolated profile still never sends; the off-toggle disarm. Update
the E2E dump word if `Word(PromptDecision)` changes, with its E2E row. Screenshot the
notice and the Options section (`shoot.ps1`, Solarized once).

**V-level:** V2 (affected suites + `check.ps1`), then CI's two required checks.

## 3. D2 — public wording and the dashboard cutover

**Merges on/after the release go**, like DRA-373 D2: `pages.yml` publishes every `site/**`
merge, so a landing page that says "on by default" before the release ships would describe
a build nobody has. D2's PR is built and reviewed ready, and merges with the release.

- `site/index.html` live caption (~line 110, *"opted-in Evolved installs only — telemetry
  is off unless a player turns it on, so each is a lower bound"*): rewrite to the new
  default, still a lower bound (people who turned it off are not counted).
- `README.md` line ~50 (*"an opt-in heartbeat, off until you say yes"*), `docs/Telemetry.md`
  and `SECURITY.md` §telemetry (*"'Not now' is final"* becomes: anyone who said Not now on an
  earlier build stays off; Options is the way back in either way).
- **Cutover note.** The jump in concurrent/active counts must not read as growth. Put a
  dated, labelled cutover marker on every surface that charts or states those numbers:
  the landing caption, the README metrics block, and any internal dashboard the Executor
  finds that reads `metrics.json`. The date is the release date, and the version is named
  ("telemetry on by default from vX.Y.Z, released YYYY-MM-DD; earlier figures counted
  opted-in installs only"). The version mix already splits by `appVersion`, so the cutover
  can also be read from the data. **No new payload field and no server schema change**. If a
  dashboard can only show this by adding a field, that is out of scope; stop and escalate.

**V-level:** V1 (docs/landing) + `LandingSiteTests` + `check.ps1`.
