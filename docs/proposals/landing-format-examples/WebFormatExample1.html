Explain
Recommended technical term: Intent classification and tool routing

This is understandable to a mixed audience while remaining technically accurate. In a more formal architecture document, it may also be described as an intent-routing or query-orchestration layer.

02
Initial prompt evaluation

Route the question before trying to answer it

The first responsibility is to classify the user's reporting intent, identify the required evidence, and dispatch the request to the most appropriate tool or workflow.

“Where can I find MDR rates for ASUs by geography, entitlement, and product over the last three fiscal quarters?”
Intent Classification and Tool RoutingClassify, constrain, decompose, and select capabilities
🔍

🧭
Metadata routeResolve MDR, ASU, geography, entitlement, and product definitions.
📊
Retrieval routeQuery the chosen semantic source with the correct time and dimensional filters.

What is being classified?

  • User goal: discovery, explanation, retrieval, output, or analysis.
  • Domain: reporting and business intelligence only.
  • Required dimensions, measures, time periods, and filters.
  • Expected output format and level of explanation.

What should the router prevent?

  • Querying a tool before selecting a trusted data product.
  • Guessing what a business term means.
  • Using a technically related but unapproved source.
  • Performing analysis when the available evidence is incomplete.
03
Reporting search experience

Data-product discovery

Answer the practical question: “Do we already have a report, cube, semantic model, or governed data solution that fits this request?”

SRC

Searchable product inventory

  • Power BI reports and semantic models
  • SSAS Tabular cubes and measures
  • Certified datasets and data marts
  • Warehouse views, macros, and curated tables
  • Repository documentation and data catalogs
FIT

Product-fit evaluation

  • Does it contain the requested measure?
  • Does it support the required dimensions?
  • Does its time grain match the question?
  • Is the data current and trusted?
  • Does the user have access?
Discovery result: “The ASU Performance semantic model is the best fit because it contains the approved MDR measure, geography hierarchy, entitlement grouping, product hierarchy, and fiscal-quarter history.”

The user receives a recommendation and rationale, not just a list of loosely related search results.

1

Candidate generation

Search names, descriptions, tags, measures, dimensions, owners, lineage, and usage patterns.

2

Relevance ranking

Score candidates against the prompt's concepts, required fields, time range, and domain.

3

Recommendation

Select the best fit, identify alternatives, and explain any missing capability or access constraint.

04
Reliable grounding

Lineage, sourcing, and business context

Once the data product is selected, the agent must understand where its information originates, how fields and measures are calculated, and what business rules apply.

Σ

Calculation and definition questions

  • How is MDR calculated?
  • Which numerator and denominator are approved?
  • Which exclusions or eligibility rules apply?
  • Which fiscal calendar is expected?
  • Are there multiple MDR variants?
↗

Source and lineage questions

  • Where does this flag originate?
  • Which macro, view, or transformation derives it?
  • Which warehouse and lakehouse objects feed the model?
  • When was the source last refreshed?
  • Who owns the logic and the reporting product?
Technical metadataTables, fields, measures, relationships, partitions, code
Lineage metadataSources, transformations, dependencies, downstream products
Semantic metadataMeasures, dimensions, hierarchies, calculation logic
Business contextDefinitions, ownership, scope, synonyms, policies, exceptions
Why context matters

“MDR rate by geography” is not executable until the workflow knows the approved MDR definition, the intended geography hierarchy, the eligible ASU population, the applicable entitlement grouping, the product taxonomy, and the required fiscal periods.

05
Intelligence extraction

Retrieve the answer from the selected product

The retrieval layer translates business phrasing into valid semantic parameters, executes against the trusted source, and returns a result set with enough evidence to support the answer.

IN

Prompt-derived parameters

  • Measure: approved MDR rate
  • Population: ASUs
  • Breakouts: geography, entitlement, product
  • Period: last three fiscal quarters
  • Output grain and sorting expectations
→
Q

Semantic execution

  • Select the trusted cube or semantic model.
  • Apply approved fields and relationships.
  • Generate DAX, MDX, XMLA, or supported query.
  • Execute within access and row-level security.
  • Return result data plus retrieval metadata.

Retrieval response should include

  • The selected product and why it was chosen.
  • The interpreted definitions and filters.
  • The results at the requested grain.
  • Refresh time, coverage, and material limitations.
  • A link back to the report or governed product where available.

Quality checkpoint

If the measure, dimensions, security, freshness, or requested grain are not supported, the workflow should stop or narrow the answer rather than silently substituting a different interpretation.

Output synthesis

Turn retrieved data into a usable deliverable

Retrieval produces evidence. Output synthesis packages that evidence for the user's intended action, from a concise answer to a shareable reporting artifact.

Advanced target: predetermined Power BI output

A reusable Power BI template can embed the approved semantic model, visual definitions, layout, branding, and parameter structure. The workflow supplies the selected filters or result context so the user receives a governed, shareable report rather than an unstructured chart.

Select template→Bind semantic model→Apply parameters→Validate visuals→Publish / share

Output selection criteria

Choose based on audience, required interactivity, repeatability, governance, sensitivity, level of detail, and whether the result needs to be shared or refreshed later.

Common output contract

Every format should preserve the product used, filters applied, refresh time, definitions, qualifications, and a traceable path back to the trusted source.

07
Interpretation layer

Move from results to directional insight

Analysis evaluates whether patterns in the retrieved data answer the business question. This layer depends heavily on contextual definitions, thresholds, baselines, and success criteria.

↕

Ranking and contribution

Identify the teams, regions, products, or categories contributing most to a result or concern.

!

Outlier detection

Find products or groups whose defect, productivity, or MDR behavior differs materially from peers or history.

≈

Trend interpretation

Determine whether movement is persistent, seasonal, isolated, or associated with a known operational event.

Example: productivity concerns

“What are the top five productivity concerns across teams?” requires an agreed productivity definition, comparison period, peer grouping, materiality threshold, and supporting measures before ranking concerns.

Example: product defects

“Which products have defect outliers?” requires the eligible product population, defect measure, volume normalization, expected range, time window, and rules for statistical or business significance.

Analytical guardrail

The agent should separate observed facts from interpretation, identify the context used, show the comparison basis, and state when the available data supports only a directional conclusion.
